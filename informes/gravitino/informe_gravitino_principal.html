4. ANÁLISIS TÉCNICO DESTACADO

4.1 Redundancia del servicio

La validación confirma explícitamente que el mínimo exigido por el plan (al menos 1 instancia) se cumple, pero que el nivel recomendado (2 instancias) no. Esto implica que, ante una falla o mantenimiento del único nodo donde corre Gravitino, el catálogo Iceberg vía REST quedaría temporalmente no disponible para los consumidores (p. ej. Trino) — riesgo operativo real, aunque no bloqueante para el estado actual de la validación.

4.2 Aislamiento de privilegios del contenedor

El contenedor de Gravitino corre como UID 0 dentro de su propio namespace, pero el host es rootless y no usa --privileged ni CapAdd, por lo que ese UID 0 se mapea a un usuario sin privilegios reales del host. Es la misma arquitectura de aislamiento usada en otros componentes Podman del proyecto (p. ej. node-exporter embebido en Alloy) y confirma que no hay privilegio real expuesto al sistema operativo base.

4.3 Versión de software: discrepancia banner vs. API

El banner del script reporta "Gravitino: 1.2.1" como versión de referencia documental, pero la versión real confirmada vía REST API (/api/version) es 1.1.0. El propio script marca esto como solo informativo, no como mínimo bloqueante. La detección de versión por inspección del contenedor (mejor esfuerzo) no logró determinarla ("unknown"), por lo que la única fuente confiable es la API — coherente con el diseño del script.

4.4 Validación funcional del ciclo de vida de metalakes

El ciclo de prueba completo (crear y eliminar un metalake vía API REST) se ejecutó exitosamente, con respuesta HTTP 200 en ambas operaciones sobre bluepoint_validacion_test, y sin dejar el metalake de prueba como artefacto residual (0 metalakes existentes antes de la prueba, ninguno después de la limpieza). Esto confirma que el endpoint de metalakes no solo responde, sino que sostiene operaciones de escritura y borrado reales.

4.5 Recursos y colocación en el nodo

El nodo pbigd-plat-apps01 reporta 4 vCPU y 15Gi de RAM, compartido con Flink JobManager, Trino Coordinator y Redis según el propio script señala como contexto de dimensionamiento. Esta colocación concentra 4 servicios en un único nodo, lo que refuerza la relevancia del WARN de redundancia en §3: la pérdida de este nodo afectaría simultáneamente a Gravitino, al JobManager de Flink y al Coordinator de Trino.
